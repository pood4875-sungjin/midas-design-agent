자연어 요구사항 → 기획서 → 디자인 컨셉 → 디자인 시스템 → 다중 페이지 UI → 프로토타입. 단순 생성이 아니라 제어 가능한 생성이 목표다.

🍳 이해를 돕는 비유   주방에 비유하면 — 주문(자연어)을 받아 판단(주방장)이 지식(레시피북)과 자원(냉장고)을 참조해 시안(요리)을 낸다. 검토 결과는 다시 정책에 반영.
왜 만드나

문제 — 생성형 도구는 결과는 내지만 제어가 안 된다

제품마다 UX 정책·디자인 시스템·화면 구조·컴포넌트 규칙이 다르다. AI에게 다 맡기면 그럴듯하지만 제품 맥락과 어긋난 결과가 나온다.

가설

모든 화면은 못 만들어도, 반복되는 영역(대시보드·목록·상세·폼·모니터링·설정)은 패턴화 가능하다.

방법

LLM은 분석·선택만. 실제 조립은 토큰·컴포넌트·패턴·레시피 기반 결정론 엔진이 한다.

드림 스테이트

역할 경계 해소. 전문가는 직접 제작 대신 기준을 정의하고 결과를 검토하는 역할로 이동.

LLM

분석 · 선택 · 시드

요구사항 분석, 패턴 선택, 컨셉·토큰 시드 생성. 토큰값까지 뱉지 않고 좁은 시드만 정한다.

지금

현재 — 온사이트 테스트베드에 DS 적재 중 NOW

전체 14칸 중 재료층(파랑) 일부만 채워졌다. 정작 판단(초록)·지식(주황)은 거의 비어있다. 이건 정상 — Phase 0은 재료(DS)를 원본 시안에서 역설계하는 단계다.

🟢 재료 — 절반

토큰 Pass A 완료. 컴포넌트(버튼·입력·GNB·드롭다운·페이지네이션) 일부. 공식 컬러·타이포 정합 반영.

🟠 지식 — 거의 빈칸

archetype 목록만 IA에 있음. UX 정책·룰은 아직. references 라이브러리는 원천으로 존재.

🟢 판단 — 텅 빔

선택룰·retrieval playbook 0. audit 루프만 가동 중. → 다음 단계의 첫 삽 대상.

📍 정확히 지금 하는 일 — 통합 프로젝트 관리 3화면(지도뷰·리스트뷰·현장 요약)의 화면 설명서를 작성하고, Figma 원본과 함께 화면을 재현해 디자인 시스템(토큰·컴포넌트)을 누적하는 중. 추출 → 재생성 → 원본과 audit 루프.
앞으로

무엇을 어떤 순서로 할 건가

원칙 — 한 화면을 끝까지 뚫어 구조를 검증한 뒤 복사. 6종 룰을 다 만들고 틀리면 전부 재작업하기 때문.

STEP 0 · 첫 대상 = 통합 프로젝트 관리 3화면 진행 중
프로젝트 선택 전 "통합 관리" 3화면 — 지도뷰 · 리스트뷰 · 현장 요약 — 부터 시작. 각 화면마다 화면 설명서(언제 쓰나 / 뼈대 / 규칙 / 상태처리)를 한 장씩 작성. AI에게 줄 설명서다.
→ docs/screen-specs/01-지도뷰 · 02-리스트뷰 · 03-현장요약
STEP 1 · 설명서 + Figma로 화면 재현 → 검증
화면 설명서(의도·규칙)와 Figma 원본(시각)을 함께 MCP에 넣어 화면 생성. 원본과 audit로 비교. 맞으면 설명서 틀이 검증된 것. 이때 나온 규칙이 곧 판단·지식 계층의 첫 내용이 된다.
→ screens/* · audit/* · 누적 토큰·컴포넌트
STEP 2 · 나머지 archetype 확장
견본 틀 그대로 Detail → Form → Report → Dashboard → Map. 매번 audit. UX 원칙·컴포넌트 누적.
→ recipes/* · ux-principles/* · 컴포넌트 Pass B
STEP 3 · 횡단 정리
status·density 직교축 규칙 확정. retrieval playbook(조회 전략). 점검 룰셋 표준화.
→ retrieval-playbook · meta · ui-rules
STEP 4 · 정책 운영틀 (나중)
정책 스키마(scope/priority). 자기진화 승격 게이트 — "왜·맥락·일반화가능?"까지 관리해야 시스템이 잘못 진화하지 않는다.
→ policy-schema
⚠️ 공통 주의 — 어떤 문서도 백지에 미리 다 쓰지 않는다. 폴더(카테고리)만 잡고, 내용은 화면이 끌어낸다. 추측으로 쓴 규칙은 원본과 안 맞아 검증할 수 없다.
