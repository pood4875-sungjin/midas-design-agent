# 온사이트 생성 정책 Agent — 설계 스펙

- **작성일**: 2026-07-02
- **상태**: 설계 승인 → 구현 플랜 대기
- **범위(1차)**: S3(온사이트 DS) → 페이지 생성. S1/S2(자연어 ingest·컨셉)는 후순위.
- **관련**: `docs/ARCHITECTURE.md`(MDA 파이프라인·철학), `onsite-designsystem/`(고정 DS), `mda-onsite-ds-sync` 스킬(토큰 값 누적)

---

## 1. 목적

PRD 입력 → 온사이트 DS를 준수하는 페이지 출력. 단, 단일 점프가 아니라 **사람이 밟는 판단 순서**를 노드로 쪼개고, 각 노드에 정책(규칙)+근거를 박아 AI가 순차 판단 → 결과가 "사람이 만든 것처럼" 나오게 한다.

핵심 동작:
- 규칙 있음 → 그대로 적용 (결정론)
- 규칙 없는 상황 → AI가 신규 규칙/패턴 제안 → **적용 전 사용자에게 물어봄** → 승인 시 기준서(rulebook)에 누적

이는 토큰 **값** 레벨에서 하던 재사용/스냅/신규추가(`mda-onsite-ds-sync`)를, **규칙/정책** 레벨로 올린 human-in-the-loop 거버넌스다.

## 2. MDA 철학 정합

> LLM = 분석·선택·판단(좁은 시드). 엔진 = 규칙대로 결정론 조립.

- LLM 역할: 결정축 판단, gap 감지·신규 규칙 제안
- 엔진 역할: 패턴→컴포넌트 레시피 결정론 조립, 슬롯 바인딩(애매할 때만 LLM 폴백)
- 규칙이 성숙할수록 LLM 개입 축소 → 재현성 상승 (수렴점: 규칙 대부분 엔진 config화)

## 3. 판단 파이프라인 (6노드)

각 노드 = 판단 + 정책(규칙 조회/적용) + gap 게이트.

| # | 노드 | 판단 내용 | 산출 |
|---|------|-----------|------|
| 1 | IA/구조 | PRD → 목적·엔티티·핵심태스크 추출 → 화면 아키타입 판정 | 아키타입 |
| 2 | 레이아웃 골격 | 아키타입 → 영역 분할(GNB/필터/본문/디테일)·밀도 | 골격+density |
| 3 | **UX 정책** | 결정축 6개 판단 → UX 패턴 선택 | 패턴 목록 |
| 4 | **컴포넌트 조합** | 패턴 → 레시피(컴포넌트·골격·슬롯바인딩·variant) | 컴포넌트 트리 |
| 5 | 토큰/스타일 | semantic 토큰 바인딩·dark/density override | 스타일 적용 트리 |
| 6 | audit | "사람이 만든 것처럼"인지 위반·누락 검증 | 검증 리포트 |

## 4. 핵심 구조 — 패턴 중간층

```
상황(PRD신호) ─Node3(결정축)─▶ 패턴 카탈로그 ─Node4(레시피)─▶ DS 컴포넌트 → 페이지
    fuzzy 판단                    매핑               결정론 조립
```

**패턴 = 경첩.** 상황판단(fuzzy)과 구현(결정론)을 분리. PRD→컴포넌트 직결의 근거 부재 문제를 해소.

### 4.1 Node 3 — 결정축(유한 목록)으로 fuzzy 규칙화

판단을 결정축 7개로 쪼갬. 축마다 "신호 조건 → 선택" 규칙 1벌.

| 결정축 | 신호(입력) | 선택지 | 규칙 예 |
|--------|-----------|--------|---------|
| 데이터 표현 | 엔티티 수·공간성·상태중심? | 맵 / 테이블 / 아코디언 / 문서 / 차트+표 / 다이어그램+표 / 표+간트 | "위치+상태 → 맵+상태리스트" |
| 필터/검색 | 필터 개수·목록 규모 | selection / dropdown / 검색바 / 컬럼필터 | "대량목록 → 검색바+컬럼필터, 소량 → 정렬 dropdown" |
| 상태 표현 | status 레벨 수 | 컬러텍스트 / 컬러마커 / 그라데이션 / 진행바 | "상태 = 컬러 텍스트(배지 pill 아님), 초과 파랑→주황→빨강" |
| 페이징 | 목록 길이·성격 | pagination / 가로스크롤 / 세로스크롤 / 아코디언 | "표 대량 → pagination, 시간그룹 → 아코디언, 문서 → 세로스크롤" |
| 밀도 | 정보량·업무맥락 | 심플 / 디테일 | 관리·결과=디테일, 온보딩·모달=심플 |
| 부가상태 | — | 빈/로딩/에러/생성중 항상 정의 | "빈칸 대신 명시 라벨(미연결/미해석)" |
| **편집상태** | 편집 가능·동시편집? | 조회 / 편집중 / 읽기전용(락) | "동일 레이아웃, 인터랙션만 토글. 락 진입은 경고 소프트락 모달 경유" |

- 산출 = 축별 결정 = **선택된 패턴 목록**
- 규칙 근거 = `~/.claude/references/ux-patterns.md` + 온사이트 IA(`docs/onsite-ia.md`) + `docs/2026-07-02-onsite-screen-bootstrap.md`(역추출 씨앗)
- 결정축은 7개로 시작(편집상태 = bootstrap에서 강한 반복 신호로 승격), 게이트로 확장 가능
- **모달은 결정축 밖**: 별도 모달 패턴 카탈로그(확인/확인+파라미터/설정폼/이력조회/경고소프트락)로 관리 (bootstrap §4)

### 4.2 Node 4 — 패턴마다 고정 레시피(결정론)

패턴 카탈로그 각 항목이 레시피를 소유:

```
패턴: "상태 모니터링 리스트"
├ 컴포넌트: [gnb, selection(필터), 리스트카드, pagination]
├ 골격: 세로스택, 필터 sticky-top, 카드 반복
├ 슬롯↔필드: {카드.title←현장명, .status←상태, .metric←계측값}   (규칙기반 + LLM 폴백)
└ variant: 상태별 카드 border = status 토큰
```

패턴 정해지면 컴포넌트·배치·바인딩 자동. LLM은 슬롯 매핑 애매할 때만 폴백(ARCHITECTURE 확정 규칙).

## 5. rulebook (기준서)

- 노드별 파일: `rules/1-ia.md … 6-audit.md`
- 패턴 카탈로그: `patterns/*.md` (기존 `onsite-designsystem/site/patterns` 개념 승격)
- **규칙 스키마 통일**: `조건 → 결정 → 근거` (근거 = references 항목 또는 온사이트 시안 출처)
- 위치: `onsite-designsystem/` 하위 후보 (구현 플랜에서 확정)

### 게이트 (human-in-the-loop)

```
노드 실행 → rulebook 조회
  ├ 매치       → 적용 (결정론)
  └ 규칙 없음  → AI 제안(규칙/패턴 초안 + 근거) → 사용자 승인? → 파일 누적 → 적용
```

## 6. bootstrap (규칙 씨앗)

- **씨앗**: 역설계 중인 온사이트 시안 — 사이트뷰 5종 + `docs/screen-specs/*` + `docs/archetype-coverage.md` 에서 사람의 판단 추출 → 규칙/패턴화
- **나머지**: PRD 돌리며 gap 게이트로 런타임 축적

## 7. 유닛 경계 (설계 명료성)

| 유닛 | 역할 | 의존 |
|------|------|------|
| Policy Kernel | 노드 순회·rulebook 조회·게이트 실행 | rulebook 파일 |
| rulebook (files) | 노드별 규칙 + 패턴 카탈로그 저장 | — |
| Decision-axis Judge (LLM) | Node3 결정축 판단 | references, IA |
| Recipe Assembler (engine) | Node4 패턴→컴포넌트 결정론 조립 | DS 컴포넌트, 토큰 |
| Gap Gate | 규칙 없음 감지·제안·승인·누적 | 사용자 |
| Auditor | Node6 검증 | 원본 시안(정답지) |

각 유닛은 파일/인터페이스로 통신, 독립 이해·테스트 가능.

## 8. 비범위 (YAGNI, 1차 제외)

- S1 자연어 ingest / S2 컨셉 3종 생성
- 단계별 서브에이전트 체인(방향 B) — 오버헤드 과함
- 규칙 전면 엔진 하드코딩(방향 C) — 규칙 성숙 후 수렴점, 지금은 이름

## 9. 열린 질문 (플랜에서 확정)

- rulebook 파일 정확한 위치·포맷(md vs json/DTCG 연계)
- Policy Kernel 실행 형태 — 스킬 / 서브에이전트 / 엔진 스크립트
- 게이트 UX — 노드별 개별 질문 vs 노드 끝 배치 승인
