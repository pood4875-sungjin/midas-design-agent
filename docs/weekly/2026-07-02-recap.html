UX 정책 파이프라인 흐름 정리

정책·규칙 → 판단 → UI 생성으로 이어지는 전체 흐름 정의. 에이전트 뼈대.

설계 · WHAT
2

온사이트 DS 탑재

온사이트 먼저 하기로 결정. 제품 DS를 에이전트에 올리는 중.

구현 · HOW
3

한국 DS 버전 테스트

한국 DS 여러 버전 가져와 탑재 후 실측. 실제로 맞물리는지 확인.

검증 · HOW
4

프로토타입

1~3 합쳐서 서비스 관점 end-to-end 전체 플로우 점검.

검증 · FLOW

어떻게 맞물리나

① UX 정책 파이프라인규칙 = 무엇을 만들지
↓
② 온사이트 DS 탑재토큰 = 어떻게
↔
③ 한국 DS 테스트탑재 결과 실측
↓
④ 프로토타입전체 서비스로 굴러가나

검증 내용 (메모리 대조)

작업검증 포인트메모리 대조 결과
① UX 정책 파이프라인 정책→판단→생성 흐름이 에이전트 뼈대로 성립하나 부분 일치 — 메모리엔 "기획→DS→멀티페이지 생성" 루프만 기록. 정책 파이프라인은 신규분.
② 온사이트 DS 탑재 온사이트 우선 + 제품 DS 누적 일치 — midas-design-agent = 온사이트 제품 DS. 충실도 규칙 존재.
③ 한국 DS 테스트 DS 값이 토큰으로 스냅·누적되나 (하드코딩 방지) 일치 — mda-onsite-ds-sync 스킬 = 토큰 누적 강제. 이걸로 검증.
④ 프로토타입 1~3 합쳐 end-to-end 서비스 흐름 성립하나 기록 없음 — Phase 0 역설계 검증 루프만 있음. 이번주 신규 점검.
주의 — ①·④는 실제 파일/커밋으로 아직 대조 안 함. 위 결과는 대화+메모리 기준. 정확한 검증 원하면 ~/midas-design-agent 리포 열어 git 로그·파일로 확인 필요.

한 줄 요약

정책(①)으로 뼈대 세우고 → DS(②③)로 살 붙이고 → 프로토타입(④)으로 서비스 전체가 굴러가나 확인. 온사이트 우선, 4개 병렬.
